(`-parallel 2`, budgets 15/25/40 min by tier). The qwen3.6 baseline is

Per task: both models failed medium-09 (count-clusters). Only qwen failed
twelve tasks (nine reasoning loops, medium-10 audit miss, hard-12 quadratic
helper, and the easy-20 instrument defect). Only nemotron failed three:
easy-13, medium-03 and hard-20, all on the performance deadline. Seven other
nemotron tasks passed but consumed their full budget without replying.

## How the failures differ

**qwen3.6 fails by not acting.** Its nine losses are one model call each,
150 to 620 KB of reasoning that never emits a tool call, at the moment it must
decide whether to delegate. Nothing gets written. Everything else it shipped
was mostly right: two logic bugs in 51 coded tasks, one quadratic helper.

**nemotron-lightning fails by acting fast and shallow.** It never looped, never
exceeded 55 KB of reasoning, and wrote code in every task. Its four failures
are all algorithmic complexity at the README's stated size:

- easy-13 and medium-03 sort with a hand-written nested swap loop (O(n²) on
  500,000 and 1,000,000 elements) instead of importing `sort`.
- hard-20 keeps a "max-heap" that pops by linear scan.
- medium-09 allocates a `rows*cols` queue for every cluster; a 500,000-cluster
  checkerboard runs out of time.

Both models sometimes avoid the `sort` package: qwen hand-rolled an insertion
sort in hard-12 after its own reasoning said "let me use sort.Ints"; nemotron
hand-rolled swap sorts in three tasks. nemotron imported `sort` in 8 of 60
solutions and `container/heap` in 3; qwen 7 and 7 of 51. Whether the READMEs'
"standard library only" line is nudging this is worth testing with a reworded
constraint.

## The silent finish is a harness interaction, and nemotron triggers it

All seven nemotron budget exhaustions end the same way: the root's last call
carries the complete summary text and a `wait_for_input` tool call. The
harness defines that tool as ending the exchange without a final reply, so the
summary is recorded as commentary, no message reaches the user, and the root
idles until the budget expires. qwen did the same once (hard-13). qwen called
`wait_for_input` 43 times in total, almost all correctly while waiting for
workers; nemotron called it 7 times, every one as its final act on a finished
task.

The cost is large: 215 of nemotron's 289 minutes. With those seven tasks ended
at their real completion time, its whole run would have taken about 1.2 hours.

Two fixes, independent of each other:

1. Harness: when `wait_for_input` arrives with substantive text and there is
   no active delegated work and no queued input, treat the text as the reply
   (or reject the call and re-prompt for a text-only response).
2. Eval runner: finish a task when all agents have been idle with no pending
   messages for a few minutes even without a root reply, flagged `no_reply`.

## Delegation

qwen delegated in 20 of 60 tasks (5 easy, 6 medium, 9 hard), with plans,
assignments and independent audits; those runs cost 3 to 9 minutes and 300K
to 730K input tokens each. nemotron never created a plan or an agent in 59
tasks. It read README and the stub, wrote the file, verified with shell, and
finished. That is why it has zero workflow-tool errors: it never called those
tools. The root prompt's instruction to use the agent workflow for any
implementation had no effect on nemotron and a partial, loop-inducing effect
on qwen.

## Verification habits

- nemotron ran `go test` in 35 of 59 tasks (79 invocations), writing throwaway
  tests through shell heredocs (43 such commands) and deleting them afterwards
  (26 `rm`). qwen's direct-mode runs ran `go test` in 15 of 40.
- Neither model tests at the README's stated sizes reliably; every nemotron
  failure and qwen's hard-12 are performance misses that a single large-input
  test would have caught.
- nemotron iterates by rewriting whole files (`write_file` on refuel.go 15
  times, evaluate.go 11 times) and misses with `edit_file` 5 times. qwen edits
  in place.

## Tool use

- nemotron's 51 tool errors are exploration mistakes: `read_pdf` on
  directories or Go files (19, and 16 tasks start with a `read_pdf` call),
  `read_file` on directories (24, mostly the workspace root), a hallucinated
  `read_workspace`, a `workdir` argument to `shell`. It treats the file tools
  as a directory listing. qwen's 6 file-tool errors were the same kind at a
  much lower rate.
- Both prefix shell commands with `cd <workspace> &&`: nemotron 366 of 466,
  qwen 234 of 330.
- nemotron replies once. qwen's delegated runs reply twice, the second a
  near-duplicate after the plan-update notification.

## Recommendations

For either model:

1. Handle `wait_for_input` with a completed summary as a reply, and add the
   `no_reply` completion rule to the runner.
2. Add one large-input check to the implementation instructions, or make the
   root ask for it, since every performance miss was at exactly the README's
   stated size.
3. Reword "standard library only" (for example "you may import any standard
   library package") and see whether the hand-rolled sorts disappear.

For qwen3.6: bound reasoning per call and reword the delegation and
"brief statement" instructions the loops quote.

For nemotron-lightning: the workflow prompt is ignored, so either accept
direct execution for tasks of this size or make delegation a hard rule; give
the file tools clearer descriptions or a `list_dir` tool so it stops probing
directories with `read_pdf` and `read_file`.

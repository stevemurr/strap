# Ladder evaluation: qwen3.6, 2026-09-14

Baseline run of the 60-task ladder (`eval/ladder`, 20 easy, 20 medium,
20 hard) against qwen3.6 served by vLLM. This document records the numbers,
the failure modes and the behavior patterns so a run with a different model
can be compared against it line by line.

## Setup

| item | value |
|---|---|
| model | `qwen3.6` (`unsloth/Qwen3.6-35B-A3B-NVFP4-Fast`) at `http://192.168.1.237:8355`, backend vllm, preset `qwen3.6-coding` (temperature 0.6, top_p 0.95, top_k 20, thinking on, max_tokens 131072) |
| harness | commit `1b6aba7`, default role prompts, local tools on, web tools off |
| runner | `strap-eval run -tier <tier> -parallel 2`, session budgets 15/25/40 min by tier, quiet period 3 s |
| run directories | `eval/results/2026-09-15-three-model-comparison/qwen3.6-thinking` (the three tier runs merged; smoke runs in `qwen3.6-thinking-smoke`) |
| reports | `strap-eval report <dir>` writes `report.md` and `report.json` in each directory |

The ladder used for this run had one instrument defect: the hidden test for
`easy-20-same-typed` declared a helper named `replay`, which collided with a
helper of the same name in the agent's solution and failed the build. After
renaming the helper the agent's untouched workspace passes, so the corrected
easy score is 20/20. The rename is in the ladder now; later runs use it.

## Failure modes, ranked by cost

### 1. Runaway reasoning loops in the root

Nine tasks (five medium, four hard; also one earlier easy smoke run) never
wrote a line of code. In each, one model call streamed 150 to 620 KB of
reasoning. The text is self-aware: "I keep saying the same thing", "I've been
going in circles for way too long", "OK, I'm going to write the code now. No
more analysis" repeated 155 times in one call.

Where it happens: seven loops on call 2 or 3, right after reading README,
go.mod and the stub, at the decide-whether-to-delegate moment; two after
`create_plan` and `create_agent`, while composing the assignment. The loops
quote the root prompt verbatim: the "Use the agent workflow when..." rule and
"Accompany the first tool batch with a brief statement of purpose" (quoted 87
times in hard-07).

Outcome depends only on the budget. The 25-minute medium budget cancels the
call. The 40-minute hard budget lets the call reach the preset's 131,072-token
output cap; the provider reports finish reason "length", the root exits, and
the harness sends the user a failure message cleanly.

Reasoning size is bimodal across all 930 completed calls: 912 under 10 KB,
eleven between 10 and 50 KB, seven between 50 and 85 KB, none above. Every
call above roughly 150 KB never completed. A cap near 100 KB would have lost
nothing observed and saved about 4.8 hours of the 7.2-hour total.

### 2. Bugs shipped without tests, in direct mode

medium-09 counts clusters with a union-find whose final loop marks the cell
index instead of its root, so snake-shaped regions count as thousands of
clusters. hard-12 reasoned "The standard library sort package is allowed. Let
me use sort.Ints" and then emitted a hand-rolled insertion sort over the unique
values, quadratic on the 500,000-element perf test. Neither task wrote a test
or ran `go test`; both verified with `go build` and `go vet` only. Of 40
direct-mode runs, 9 wrote a test file and 15 ran `go test` at all.

### 3. Audits pass everything

All 17 audits returned pass with zero findings. Their summaries describe
rerunning the implementor's tests and reading the code. medium-10 shows the
gap: the root's plan step listed "error for unknown target in deps", the
implementor returned early on empty targets before validating deps, and the
auditor passed it.

### 4. Silent success

hard-13 was implemented, audited and accepted by minute 4. The root updated the
plan, went idle and never replied to the user, so the session idled for 36
minutes until the budget expired. It passed on grade.

### 5. Server hiccups, handled well

hard-08: the implementor's request died with a connection EOF; the root
received the failure notice, created a new implementor, reassigned the work,
and the task passed. hard-19: the root's sixth call hit a TCP read timeout after
the code was written; the root reported failure to the user and the task passed
anyway. Both happened while the other parallel session was probably in a
runaway call.

## Behavior patterns

- Delegation is the exception. The root did the work itself in 40 of 60 tasks
  despite its prompt: delegated in 5 easy, 6 medium and 9 hard. Direct mode
  passed 31 of 40 (corrected); its failures were 7 loops and 2 untested bugs.
  Delegated passed 17 of 20, losing 2 loops during assignment and the missed
  audit.
- Cost by mode. Healthy direct runs take about a minute and 40 to 90K input
  tokens. Delegated runs take 3 to 9 minutes, 30 to 70 calls and 300 to 730K
  input tokens, almost all from re-sending a context that never exceeds 23K
  tokens.
- Every delegated run replies twice: a full summary, then a near-duplicate
  "final status" 6 to 10 seconds later after the plan-update notification wakes
  the root again.
- Idle agents. Four delegated runs created an agent that never received work:
  hard-13 and hard-16 created two auditors and used one; medium-14 and hard-14
  created an implementor and then looped.
- Workflow tools cause almost all tool errors. 50 of 54 tool errors were on the
  harness's own work tools: `report_work_progress` 26 (missing
  `assigned_at_revision` or `work_id`, "observed finding requires evidence"),
  `create_plan` 12 (missing `title`, `steps` not an array), `assign_work` 4
  (mixing the two argument forms), `submit_work` 2 (steps not ready for
  review), a hallucinated `read_work` twice, `get_work_progress` 1,
  `get_audit` 1. File tools: 4 `read_file` errors (README guessed one directory
  up, or a directory path), 2 `edit_file`.
- Shell habits. 234 of 330 shell commands begin with `cd <workspace> &&` even
  though the tool already runs there; 82 are `find` or `ls` exploration. Eight
  runs deleted their own scratch test file before finishing.
- Every run read README.md and go.mod first (88 and 71 reads across 60 tasks).

## Suggested changes

1. Bound reasoning per call, with `-max-tokens` on the run or a harness
   watchdog that cancels a call past a reasoning threshold and re-prompts.
2. Reword the root prompt's delegation rule and the "brief statement"
   requirement; the loops are stuck on those two sentences.
3. In the eval runner, finish a task when all agents are idle and all work is
   accepted for a few minutes even without a root reply, flagged `no_reply`.
4. Make audits adversarial: require at least one new test against the README
   contract rather than rerunning the implementor's suite.
5. Tighten the three work-tool schemas behind 42 of the errors.
6. Prefix the shared hidden-test helpers (`brute` in 40 files, `check` in 3)
   to prevent the easy-20 style false failure.

## Comparing another model

Run the same three commands with the other profile and keep the run
directories:

```sh
./strap-eval run -tier easy   -parallel 2 -profile <name>
./strap-eval run -tier medium -parallel 2 -profile <name>
./strap-eval run -tier hard   -parallel 2 -profile <name>
./strap-eval report eval/results/<dir>
```

Compare on the same axes: pass rate per tier, tasks that produced no code,
share of wall clock in timed-out tasks, the reasoning-size distribution of
completed calls, direct versus delegated counts and pass rates, tool errors by
tool, audit verdicts and findings, replies per task, and the specific tasks
that failed here (medium-09, medium-10, hard-12 for correctness; the nine loop
tasks for stability). The per-task numbers in each `report.md` and the raw
metrics in `report.json` line up column for column between runs.
